# 云端与单机：职责边界

> 目的：避免把云端版的多人治理/审批逻辑塞进单机版，也避免把单机版的“方向会话隔离”误当成云端治理。
> 结论：**云端管治理与责任，单机管方向连续性与上下文卫生。两者共享“方向层/操作层分离”，但不共享审批对象。**

## 1. 一句话划分

| 版本 | 一句话 | 核心问题 |
|---|---|---|
| 云端 SuperAgentPlus | 多人/多角色围绕项目做可追责的交付 | 谁有权决定、谁验收、证据是否可信、组合是否成立 |
| 单机 SuperAgentPlusLocal | 一个人用多个会话做项目，保持方向不被细节淹没 | 哪些信息该进总工上下文、哪些必须留在工作会话 |

**单机没有“审批”这回事。** 没有 G1/G2/G3、没有 approve/reject、没有 lease/grant/contract 审批链；单机的“总工”是**方向会话**，不是审批人。

## 2. 对象对照

| 维度 | 云端 | 单机 |
|---|---|---|
| 核心对象 | Goal、Intent、Decision、Contract、Task、Attempt、Lease、Evidence、Acceptance、Release | Direction、Brief、DirectionNote、Session、WorkLog |
| 决策 | 多人讨论、G3 方向/结构裁决、Decision 版本 | 总工会话写方向笔记；用户可采纳/不采纳 |
| 验收 | G1 操作者初审 + G2 独立验收 + G3 方向裁决 | **无审批**；工作会话自测，用户自己判断 |
| 证据 | 正式证据链、哈希、复核、集成 | 轻量引用；不要求正式证据包 |
| 并发 | 多 worker 认领、租约、fencing、幂等 | 多会话并行；只需避免同时写同一个 brief/note |
| 失败重点 | 越权、错验收、组合失败、责任不清 | 上下文污染、方向漂移、会话丢状态 |
| 隔离手段 | 角色权限 + 过滤读模型 + 审计 | 独立 session/工作区；`direction/briefs/notes` 与 `work/` 分离 |
| 审计 | 不可变事件、责任链 | 可选轻量记录；不承诺不可篡改 |

## 3. 共同点（只保留一条）

**方向层与操作层分离：**

- 方向层（总工/Direction）：目标、原则、结构、优先级、风险、待定问题。
- 操作层（worker/WorkLog）：代码、diff、日志、复现、调试过程。
- 方向层默认不读操作层；需要细节时，由人手动提供**限定范围/时限**的摘录，而不是自动灌入。

这条原则云端和单机都适用；但云端还要在此之上加多人治理，单机不加。

## 4. 单机不是什么

- 不是“云端的精简审批流”：没有 G1/G2/G3，没有 approve/reject。
- 不是“总工替用户拍板”：总工给方向笔记，用户自己决定。
- 不是“多租户/多用户”：一个用户、一个项目、多个会话。
- 不是“证据链系统”：不要求哈希、复核、集成门禁。

## 5. 云端不是什么

- 不是“单机的放大版”：云端不能假设只有一个用户、一个方向会话。
- 不能把“总工只看简报”当成“总工不承担责任”：云端的 G3 是正式裁决，要记录 brief/方向包版本。
- 不能把单机的 `DirectionNote` 直接当云端 `Decision`：前者是个人方向笔记，后者需要多人确认/版本。

## 6. 迁移边界

- 单机 → 云端：可以把 `direction.md` 导出为 Goal/Decision 草案，把 `brief/note` 作为讨论材料；但不能自动变成已批准 Decision。
- 云端 → 单机：可以把云端 Decision 摘要成 `direction.md`；但不要把 Contract/Lease/Evidence 全套搬进 `.sap.local`。
- 两边都保留“方向简报一页、操作细节不进方向会话”的格式，便于人工迁移。

## 7. 设计检查

- 单机文档里出现 `approve/reject/G1/G2/G3/lease/grant/acceptance` → 说明又把云端模型塞进来了。
- 单机总工会话里出现 stack trace/diff/日志 → 污染，需退回工作会话。
- 云端文档里出现“单机总工自己批就行” → 越权，需补多人/证据/裁决。
- 单机 `direction/briefs/notes` 与 `work/` 混在一起 → 隔离失败。
